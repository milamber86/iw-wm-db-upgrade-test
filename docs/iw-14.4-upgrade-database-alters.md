# IceWarp 14.3 → 14.4 upgrade: database ALTER guide for large datasets

This guide is for DBAs and operators planning the **14.3 → 14.4** IceWarp upgrade on instances with
large mailbox databases. It explains **which MySQL settings change ALTER durations**, gives
**expected times by table size**, shows how to **pre-apply the heavy `item` rebuild** with
`pt-online-schema-change` (after widening `folder`), and covers **replicated topologies**.

Everything below assumes InnoDB and IceWarp's split databases (accounts, groupware, directory cache,
EAS, WebClient, antispam). Replace `<wc_db>` with the WebClient database name (commonly
`dbiwc…wc`) and `<acc_db>` with the accounts database.

> **The `item` table dominates the window.** In a measured 14.4 upgrade of a 35.2 M-row `item`
> table, the whole schema migration produced **one** long statement — the `item` rebuild — taking
> **62 minutes**, while every other change was seconds or less. Plan the window around `item`.

---

## 1. What the 14.4 upgrade actually changes

| Database | Object | Change | Cost |
|----------|--------|--------|------|
| WebClient (`<wc_db>`) | `item` | INT → BIGINT (`folder_id`, `item_id`, `size`, `source_folder_id`, `dummy_id`), add `summary`, `i_thread_id`, `is_thread_latest`, add `FK_item_folder`, `FK_i_item_thread` | **full table rebuild (COPY)** — the only heavy statement |
| WebClient | `folder` | `folder_id`, `parent_folder_id`, `sync_in_progress_folder_id` → BIGINT | COPY too (type change), but the table is small — 1.5–2 s measured |
| WebClient | `folders` | add `own_acc_id`, drop legacy indexes/columns, add `FK_f_folder` | small, mostly INPLACE |
| WebClient | `snoozed_item` | drop `snoozed_item_ibfk_1`/`IDX_snoozed_date`, `snoozed_item_id` → BIGINT, add `snoozed_acc_id`, add FKs | usually tiny/empty |
| WebClient | `thread` | add `FK_t_account`, `FK_t_latest_item` | fast |
| GroupWare | `Event` | `EvnURL` → MEDIUMTEXT/TEXT | COPY, but `Event` is far smaller than `item` |
| GroupWare | `Conference`, `TeamChat*`, `OnlineDocumentEditing`, … | new tables / additive columns | fast |

The `item` rebuild is a **COPY** because it changes column types: INT→BIGINT cannot be INSTANT and
cannot be INPLACE, so MySQL must build a new table and copy every row.

Measured example (16 vCPU test bed, 96 GB buffer pool, local NVMe, MySQL 8.0, ProxySQL in front):

```
version      14.3.0.13 -> 14.4.0.0
installer    1h 29m total
WebClient v2 "Migrate database to new WebClient v2"   18:57:39 -> 20:24:13
  ALTER TABLE item …                                 1h 02m 07s  (35,206,106 rows)
all other ALTERs                                     < 3 s each
```

## 2. Which MySQL settings affect ALTER time

### 2.1 The three that matter most

1. **Redo log capacity.** A small redo log forces frequent checkpoints while the copy inserts
   millions of rows. A large redo log lets InnoDB batch writes; on big tables this is often the
   single largest win.
2. **Doublewrite.** `innodb_doublewrite=ON` writes every page twice — pure write amplification for a
   rebuild. Disabling it for the window (only if the storage/BBU is reliable) is a large win.
3. **Binary log — but read this carefully.** A native `ALTER` is replicated as a **single statement**,
   so the binlog itself adds little to the rebuild; most of the win people attribute to
   `sql_log_bin=0` on big ALTERs is really redo/doublewrite/IO. The real binlog cost comes from the
   **data** movement around the ALTER: the migration's orphan `DELETE`, and above all
   `pt-online-schema-change`, which copies every row with `INSERT`s and is therefore fully
   row-logged. Disabling the binlog is only an option on a **standalone** server — see section 5.

Also significant: `innodb_flush_log_at_trx_commit` (fewer commit fsyncs; the rebuild commits once, so
the gain is moderate, but the surrounding upgrade work has many small transactions) and the DDL
parallelism settings.

### 2.2 Recommended settings for the window

```ini
[mysqld]
# ---- speed knobs for the 14.4 schema migration; revert afterwards ----
skip-log-bin                       # STANDALONE ONLY — breaks replication on a primary (see §5)
innodb_redo_log_capacity      = 16G   # MySQL 8.0.30+; older: innodb_log_file_size=8G + innodb_log_files_in_group=2
innodb_flush_log_at_trx_commit = 2    # 2 (or 0) while durability is not required
innodb_doublewrite            = OFF   # revert to ON after the window
innodb_io_capacity            = 4000  # match the device (NVMe: 4000-8000)
innodb_io_capacity_max        = 8000
innodb_ddl_threads            = 8     # 8.0.27+; parallel index build / DDL sort
innodb_ddl_buffer_size        = 256M  # per-thread DDL sort buffer
innodb_parallel_read_threads  = 8     # 8.0.14+; parallel clustered-index scans
innodb_buffer_pool_size       = 96G   # size to the working set, not to the table
```

| Setting | Effect on a COPY/ALTER | Notes |
|---------|------------------------|-------|
| `log_bin` / `skip-log-bin` | Small for a native COPY (one statement in the binlog); **large for pt-osc** (row copies). | Restart required. **Never `skip-log-bin` on a primary with replicas.** If binlogs must stay on, consider `sync_binlog=0` and `binlog_row_image=minimal` for the DML phases. |
| `sync_binlog` | Moderate for DML-heavy phases. | One fsync per transaction; a native rebuild is one transaction, pt-osc is many. |
| `innodb_redo_log_capacity` / `innodb_log_file_size` | **Large.** Fewer checkpoints during bulk inserts. | 8.0.30+ uses the single capacity variable (dynamic); older builds need a restart. |
| `innodb_flush_log_at_trx_commit` | Moderate. | Affects commit fsyncs; more relevant for pt-osc and the upgrade's many small transactions than for one rebuild. |
| `innodb_doublewrite` | **Large.** Halves write amplification. | Only safe on reliable storage; revert to `ON`. |
| `innodb_io_capacity` / `_max` | Moderate. | Lets background flushing keep up with the copy; default values are tuned for slow disks. |
| `innodb_ddl_threads`, `innodb_ddl_buffer_size` | Moderate for index-building phases. | Most effective for INPLACE `ADD INDEX`; the `item` copy also builds indexes at the end. |
| `innodb_parallel_read_threads` | Moderate. | Parallel scan for `CHECK`/`ALTER`; main benefit on large tables. |
| `innodb_buffer_pool_size` | Moderate to large. | Keeps secondary indexes and the primary key cached. Do not exceed RAM minus overhead. |
| `old_alter_table` | **Small for `item`, but keep it `OFF`.** | `ON` forces the legacy copy path. It does not make the `item`/`folder` type-change copies faster — those already require COPY — but it removes INPLACE for the additive steps (`folders`, `thread`, `ADD FOREIGN KEY`), turning second-level metadata changes into rebuilds. |
| `foreign_key_checks` | Leave `ON`. | Disabling it lets `ADD FOREIGN KEY` skip validation. The 14.4 migration relies on the constraints being real. |
| `lower_case_table_names` | Not a timing factor. | Must already be 1 (set at initialization); never change it afterwards. |

**Not a factor:** ProxySQL, the network path, or connection multiplexing. Measured A/B on identical
data: `item` rebuild **188 s via ProxySQL vs 203 s direct** — within noise. Tune the MySQL server,
not the proxy.

### 2.3 Applying the settings

Most of these require a restart, which the maintenance window already provides. Restart MySQL once,
**before** starting the 14.4 installer, then run the upgrade, then revert and restart again.

Session-scoped knobs are only useful for statements you run yourself (the pre-alters in section 4);
the installer opens its own connections, so server-wide settings are what count for the 14.4
migration itself.

## 3. Typical ALTER times

Times for the `item` rebuild alone, with the settings from section 2.2, on a modern server
(NVMe, 16+ vCPU, buffer pool large enough for the hot indexes):

| Rows in `item` | Rebuild time | Approx. per row |
|----------------|--------------|-----------------|
| 1 M | ~1 min | ~60 µs |
| 3 M | ~4 min | ~80 µs |
| 5 M | ~7 min | ~84 µs |
| 10 M | ~14 min | ~84 µs |
| 15 M | ~21 min | ~84 µs |
| 35 M | ~62 min | ~106 µs |

Rules of thumb:

- Up to ~15 M rows the cost is close to **85 µs/row** and scales linearly.
- Above ~15 M rows expect a **25 % tail** (≈105 µs/row) from larger indexes and checkpoint pressure.
- Estimate your own: `seconds ≈ rows × 0.085` up to 15 M, then `rows × 0.105`.
- These are for a **single** `item` rebuild. Other tables add seconds, not minutes — except
  `Event` on GroupWare, which is a COPY too but typically 10–50× smaller.
- Halve the numbers if you remove the binary log *and* the doublewrite; expect 1.5–2× the numbers
  with default durability settings on a busy server.

## 4. Pre-applying the heavy changes (folder first, then item)

The `item` change is **backwards compatible with IceWarp 14.3**: 14.3 reads and writes
`folder_id`/`item_id`/`size`/`source_folder_id`/`dummy_id` as integers, and MySQL converts them to
and from BIGINT transparently. The added columns (`summary`, `i_thread_id`, `is_thread_latest`) are
either nullable or have defaults, so 14.3 simply ignores them.

Do this **ahead of the maintenance window** (a quiet period is enough), and the 14.4 migration will
find the columns already widened and only apply what is still missing.

**Order matters: widen `folder` first, then `item`.**

- `folder` is small, so it is quick.
- 14.3 joins `item.folder_id = folder.folder_id`. Widening `item` while `folder` is still INT leaves
  the join with mixed types; depending on the query plans, 14.3 can lose index usage and slow down.
  Do both back-to-back (same session/day) to keep the window of mixed types as short as possible.
- `item`'s new FK will reference `folder(folder_id)`, so the parent must be BIGINT by the time the
  14.4 installer adds the constraint.

### 4.1 What to pre-apply — and what not to

Pre-apply the **column definitions and the three new indexes**:

- `folder` — `folder_id`, `parent_folder_id`, `sync_in_progress_folder_id` → BIGINT (section 4.3).
- `item` — the MODIFY/ADD COLUMN part of the 14.4 statement **and** the three indexes the migration
  creates (`IDX_item_message_id`, `IDX_item_thread_latest`, `IDX_item_thread_id`, section 4.4).

**Do not pre-create the foreign keys.** `FK_item_folder` references `folder(folder_id)` and
`FK_i_item_thread` references `thread(thread_id)`; both parents are produced by the 14.4 migration.
Let the installer add them.

The full 14.4 `item` change, for reference. You pre-apply everything except the two foreign keys:

```sql
ALTER TABLE item
  MODIFY COLUMN folder_id          BIGINT NOT NULL,
  MODIFY COLUMN item_id            BIGINT NOT NULL AUTO_INCREMENT,
  MODIFY COLUMN size               BIGINT NOT NULL,
  MODIFY COLUMN source_folder_id   BIGINT,
  MODIFY COLUMN dummy_id           BIGINT,
  ADD COLUMN summary               VARCHAR(512),
  ADD COLUMN i_thread_id           BIGINT,
  ADD COLUMN is_thread_latest      INTEGER DEFAULT 1 NOT NULL,
  ADD INDEX IDX_item_message_id    (message_id),
  ADD INDEX IDX_item_thread_latest (folder_id, is_thread_latest, `date`),
  ADD INDEX IDX_item_thread_id     (i_thread_id),
  ADD CONSTRAINT FK_item_folder FOREIGN KEY (folder_id) REFERENCES folder (folder_id)
      ON DELETE CASCADE ON UPDATE CASCADE,
  ADD CONSTRAINT FK_i_item_thread FOREIGN KEY (i_thread_id) REFERENCES thread (thread_id);
```

In the measured migration the three indexes are issued as separate `CREATE INDEX` statements;
folding them into the pre-alter is equivalent and lets one table pass build them all.

If the indexes already exist when 14.4 runs, the installer logs
`Error executing query: Duplicate key name 'IDX_item_message_id'` and continues — that is the
expected "already done" path, not a failure. The same happens for the indexes 14.3 already has
(`IDX_item_date`, `IDX_item_list`, …).

### 4.2 Install `pt-online-schema-change`

Percona Toolkit ships `pt-online-schema-change`; it needs Perl and Perl's MySQL driver.

**RHEL / Rocky / AlmaLinux 8–9:**

```bash
sudo dnf install -y https://repo.percona.com/yum/percona-release-latest.noarch.rpm
sudo percona-release enable tools release
sudo dnf install -y percona-toolkit
```

**Debian / Ubuntu:**

```bash
wget https://repo.percona.com/apt/percona-release_latest.generic_all.deb
sudo dpkg -i percona-release_latest.generic_all.deb
sudo apt-get update
sudo apt-get install -y percona-toolkit
```

**No repository access** (air-gapped, DB appliance, or the DB host is not yours to install on):
download the tarball for your architecture from
<https://www.percona.com/downloads/percona-toolkit/>, then:

```bash
tar xzf percona-toolkit-*.tar.gz
sudo install -m 0755 percona-toolkit-*/bin/pt-online-schema-change /usr/local/bin/

# the tool also needs Perl DBI and DBD::mysql
sudo dnf install -y perl-DBI perl-DBD-MySQL          # RPM based
# sudo apt-get install -y libdbi-perl libdbd-mysql-perl   # Debian based
```

Verify:

```bash
pt-online-schema-change --version
pt-online-schema-change --help | head -5
```

Expected: `pt-online-schema-change 3.x` (3.5 or newer; 3.7.x is current). If it fails with
`Can't locate DBD/mysql.pm`, the Perl MySQL driver is missing — install `perl-DBD-MySQL` (RPM) or
`libdbd-mysql-perl` (deb).

Run it **from a host that can reach MySQL directly** (not through ProxySQL): pt-osc needs
`SHOW PROCESSLIST`/`SHOW REPLICA STATUS`-style access and a stable connection for hours.

**Replica discovery for `--recursion-method`.** pt-osc can find replicas with
`--recursion-method=processlist` or `hosts`, but on managed clusters both often fail (no
`SHOW SLAVE HOSTS`, restricted `PROCESSLIST`). The reliable method is a DSN table:

```sql
CREATE DATABASE IF NOT EXISTS percona;
CREATE TABLE IF NOT EXISTS percona.dsns (
  id        int(11)      NOT NULL AUTO_INCREMENT,
  parent_id int(11)      DEFAULT NULL,
  dsn       varchar(255) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

INSERT INTO percona.dsns (dsn) VALUES
  ('h=192.0.2.11,P=3306,u=ptosc,p=<password>'),
  ('h=192.0.2.12,P=3306,u=ptosc,p=<password>');
```

then pass `--recursion-method=dsn=D=percona,t=dsns` (see section 5). A socket can be used instead of
host/port (`S=/var/lib/mysql/mysql.sock`), and the account needs `PROCESS` + `REPLICATION CLIENT` on
the replicas so pt-osc can read their lag.

### 4.3 Step 1 — widen `folder`

Inspect what you are about to change and whether anything references `folder`:

```sql
SELECT column_name, column_type, is_nullable, column_key, extra
FROM information_schema.columns
WHERE table_schema = '<wc_db>' AND table_name = 'folder'
  AND column_name IN ('folder_id','parent_folder_id','sync_in_progress_folder_id');

SELECT table_rows, ROUND((data_length + index_length) / 1024 / 1024) AS mb
FROM information_schema.tables
WHERE table_schema = '<wc_db>' AND table_name = 'folder';

-- child FKs pointing at folder (usually none before the 14.4 migration)
SELECT constraint_name, table_name, column_name
FROM information_schema.key_column_usage
WHERE table_schema = '<wc_db>' AND referenced_table_name = 'folder';
```

`folder` is normally small (thousands to a few hundred thousand rows; a ~20 k-row `folder` took
**1.5–2 s** in our measurements), so a plain `ALTER` is usually the simplest option:

```sql
SET SESSION old_alter_table = 0;
SET SESSION lock_wait_timeout = 60;
ALTER TABLE folder
  MODIFY COLUMN folder_id                BIGINT NOT NULL AUTO_INCREMENT,
  MODIFY COLUMN parent_folder_id         BIGINT,
  MODIFY COLUMN sync_in_progress_folder_id BIGINT;
```

If `folder` is large, or you cannot take even a short metadata lock, use pt-osc instead:

```bash
pt-online-schema-change \
  --alter "MODIFY COLUMN folder_id BIGINT NOT NULL AUTO_INCREMENT, \
           MODIFY COLUMN parent_folder_id BIGINT, \
           MODIFY COLUMN sync_in_progress_folder_id BIGINT" \
  --alter-foreign-keys-method=rebuild_constraints \
  --no-check-alter \
  --chunk-time=0.5 \
  --max-load Threads_running=50 \
  --critical-load Threads_running=100 \
  --print \
  --dry-run \
  h=<db_host>,P=<port>,u=<user>,p=<password>,D=<wc_db>,t=folder
```

Review the printed statements, then re-run with `--execute` instead of `--dry-run`.

Verify the result before moving on:

```sql
SELECT column_name, column_type
FROM information_schema.columns
WHERE table_schema = '<wc_db>' AND table_name = 'folder'
  AND column_name IN ('folder_id','parent_folder_id','sync_in_progress_folder_id');
-- expect bigint / bigint / bigint
```

Widening `folder` is **not** a rollback-friendly change (narrowing BIGINT→INT would have to prove no
value exceeds the INT range). Take a backup first; if you need to abort the upgrade, keep the
widened schema — 14.3 runs fine on it.

### 4.4 Step 2 — widen `item` with `pt-online-schema-change`

Prerequisites:

- Step 1 done (`folder` is BIGINT).
- `snoozed_item_ibfk_1` dropped first — 14.3 has a child FK pointing at `item`, and pt-osc must be
  able to swap the table. The full ordered sequence is in
  [`docs/pre-upgrade-bigint.md`](pre-upgrade-bigint.md).
- No triggers on `item` that you do not own.
- Free disk **≥ 2× the table size** (shadow table + original) — and on every replica (section 5).
- A backup/restore point — the conversion is not practically reversible.

```bash
pt-online-schema-change \
  --alter "MODIFY COLUMN folder_id BIGINT NOT NULL, \
           MODIFY COLUMN item_id BIGINT NOT NULL AUTO_INCREMENT, \
           MODIFY COLUMN size BIGINT NOT NULL, \
           MODIFY COLUMN source_folder_id BIGINT, \
           MODIFY COLUMN dummy_id BIGINT, \
           ADD COLUMN summary VARCHAR(512), \
           ADD COLUMN i_thread_id BIGINT, \
           ADD COLUMN is_thread_latest INTEGER DEFAULT 1 NOT NULL, \
           ADD INDEX IDX_item_message_id (message_id), \
           ADD INDEX IDX_item_thread_latest (folder_id, is_thread_latest, `date`), \
           ADD INDEX IDX_item_thread_id (i_thread_id)" \
  --alter-foreign-keys-method=rebuild_constraints \
  --no-check-alter \
  --chunk-time=0.5 \
  --max-load Threads_running=50 \
  --critical-load Threads_running=100 \
  --pause-file=/tmp/pt-osc.pause \
  --print \
  --dry-run \
  h=<db_host>,P=<port>,u=<user>,p=<password>,D=<wc_db>,t=item
```

Review the `--dry-run` output, then run the same command with `--execute` instead of `--dry-run`.

Notes:

- `--no-check-alter` is required because the primary key type changes; pt-osc's warning is expected.
- `--alter-foreign-keys-method=rebuild_constraints` handles child tables (`snoozed_item`) that point
  at `item`; `auto` is fine once that FK is dropped.
- `--chunk-time=0.5` keeps each chunk under half a second; `--max-load`/`--critical-load` throttle
  or abort based on `Threads_running`.
- `--pause-file` lets you pause the copy (create the file) to relieve a busy server; remove it to
  resume.
- On a **replicated** primary do **not** add `--set-vars "sql_log_bin=0"` — the copied rows would
  never reach the replicas (section 5).
- pt-osc keeps 14.3 online; the final `RENAME` takes a brief metadata lock (seconds).

### 4.5 What a successful run looks like — the `item` rebuild

Example for the `item` table (35,384,508 rows, as restored from a production dump), with replica
discovery through the DSN table from section 4.2:

```bash
pt-online-schema-change \
  --alter "MODIFY COLUMN folder_id BIGINT NOT NULL, \
           MODIFY COLUMN item_id BIGINT NOT NULL AUTO_INCREMENT, \
           MODIFY COLUMN size BIGINT NOT NULL, \
           MODIFY COLUMN source_folder_id BIGINT, \
           MODIFY COLUMN dummy_id BIGINT, \
           ADD COLUMN summary VARCHAR(512), \
           ADD COLUMN i_thread_id BIGINT, \
           ADD COLUMN is_thread_latest INTEGER DEFAULT 1 NOT NULL, \
           ADD INDEX IDX_item_message_id (message_id), \
           ADD INDEX IDX_item_thread_latest (folder_id, is_thread_latest, `date`), \
           ADD INDEX IDX_item_thread_id (i_thread_id)" \
  --alter-foreign-keys-method=rebuild_constraints \
  --recursion-method=dsn=D=percona,t=dsns \
  --no-check-replication-filters \
  --no-check-alter \
  --chunk-time=0.5 \
  --max-load Threads_running=100 \
  --critical-load Threads_running=160 \
  --max-lag=30 \
  --pause-file=/tmp/pt-osc.pause \
  --execute \
  D=<wc_db>,t=item,u=<user>,h=<primary_host>,p=<password>
```

Output. The sequence of lines is exactly what pt-osc prints; the `T+…` offsets are illustrative —
the copy phase is the one that runs for hours and its pace is set by your `--max-load`/`--max-lag`
settings, not by the server's maximum throughput:

Reading the output:

| Line | Meaning |
|------|---------|
| `Found 2 slaves` / `Will check slave lag on` | Replica discovery worked through `percona.dsns`. The copy pauses when lag exceeds `--max-lag` (here 30 s). `Cannot connect to ...` means the DSN table is wrong or the account lacks `PROCESS`/`REPLICATION CLIENT` on the replicas. |
| `# 6 software updates are available` | A version nag (MySQL, DBD::mysql, Toolkit, Perl). Harmless; silence it with `--no-version-check`. |
| `Operation, tries, wait` | The retry policy per phase: up to 10 attempts, with the listed wait between them. |
| `Altering …`.`item` | Start. `_item_new` will grow to roughly the size of `item` — see the disk requirement in section 4.4. |
| `Creating new table` / `Altered …_item_new` | The shadow table is created and altered **empty**; this is instant and does not touch the data. |
| `Creating triggers` / `Created triggers OK` | Three triggers on `item` mirror INSERT/UPDATE/DELETE into `_item_new` for the whole copy. This is why **IceWarp must not be restarted to run its own DDL on `item`** while pt-osc works, and why the copy slows down under write load. |
| `Copying approximately 35384508 rows` → `Copied rows OK` | The dominant phase. Deliberately throttled by `--chunk-time=0.5`, `--max-load`, `--critical-load` and `--max-lag`: for tens of millions of rows expect **hours**, not minutes. For reference, the native 14.4 rebuild of 35.2 M rows took **62 min** with no triggers and no chunking — pt-osc will be slower than that. The shadow table carries the three new indexes from the start, so every copied row also maintains them. |
| `Analyzing new table` | Refreshes statistics before the swap. |
| `Swapping tables` / `Swapped … OK` | The only moment IceWarp can stall: the `RENAME` takes a metadata lock. Normally sub-second, but a long-running transaction on `item` delays it. |
| `Dropping old table` / `Dropping triggers` | Cleanup. `_item_old` keeps its disk space until this line. |
| `Successfully altered …` | Done. Refresh statistics (section 4.6), verify (section 4.7), then run the 14.4 installer (section 4.8). |

For `item` you must **not** see:

```text
No foreign keys reference `<wc_db>`.`item`; ignoring --alter-foreign-keys-method.
```

`snoozed_item_ibfk_1` points at `item`, so pt-osc either prints
`Will update foreign keys on ...` (it will rebuild that child FK — an extra ALTER on the small
`snoozed_item` table) or, if you already dropped the FK as in section 4.4, there is nothing to do.
The "No foreign keys reference" line only makes sense on tables nothing points at.

If pt-osc aborts (critical load, replica lag, lost connection), it drops its triggers but may leave
`_item_new` / `_item_old`. Check for them and `DROP TABLE` before retrying:

```sql
SHOW TABLES FROM `<wc_db>` LIKE '\_item\_%';
```

### 4.6 Refresh statistics with `ANALYZE TABLE`

The rebuild leaves the new table with fresh statistics, but two things move them out of date: the
migration deletes orphaned `item` rows, and any bulk work around the window changes the data
distribution. `innodb_stats_auto_recalc` only re-samples after roughly 10 % of the rows change, so
make it explicit.

Run it **after the pre-alters** (pt-osc already runs `ANALYZE` on the swapped-in table, so this is a
cheap confirmation) and again **after the 14.4 installer finishes**, before IceWarp goes back into
full service:

```sql
-- the heavy one
ANALYZE TABLE `<wc_db>`.`item`;

-- the rest of the WebClient tables the migration touches
ANALYZE TABLE `<wc_db>`.`folder`,
              `<wc_db>`.`folders`,
              `<wc_db>`.`snoozed_item`,
              `<wc_db>`.`thread`;

-- GroupWare side (Event is the only large COPY there)
ANALYZE TABLE `<gw_db>`.`Event`;
```

What to expect and how to read it:

- Each table returns one status row (`status: OK`). `note: Table is already up to date` is also fine —
  MySQL considers the statistics current.
- `ANALYZE TABLE` reads index pages to sample; it does not modify data. On InnoDB (8.0) it uses the
  INPLACE algorithm and takes a brief shared metadata lock at the start and end — run it in a quiet
  moment, not at peak.
- Cost is small next to the rebuild: by default 20 sample pages per index, so a 58 GB `item` with ten
  indexes takes seconds to a couple of minutes.
- For very large tables, raise the sample first (dynamic, applies to the next `ANALYZE`), then
  re-run the statements above:

  ```sql
  SET GLOBAL innodb_stats_persistent_sample_pages = 100;   -- default 20; revert afterwards
  ```

Verify that the statistics are current:

```sql
SELECT table_name, last_update, n_rows, clustered_index_size, sum_of_other_index_sizes
FROM mysql.innodb_table_stats
WHERE database_name = '<wc_db>' AND table_name = 'item';

SELECT index_name, cardinality
FROM information_schema.statistics
WHERE table_schema = '<wc_db>' AND table_name = 'item'
ORDER BY index_name, seq_in_index;
```

`last_update` should be the time of your `ANALYZE`, `n_rows` should be close to the real row count,
and every index should have a non-`NULL` `cardinality` (a `NULL` means that index was never
sampled). Keep `innodb_stats_persistent=ON` (the default) so the statistics survive a restart.

### 4.7 Verify before running the installer

```sql
SELECT table_name, column_name, column_type
FROM information_schema.columns
WHERE table_schema = '<wc_db>'
  AND ( (table_name = 'item' AND column_name IN
          ('folder_id','item_id','size','source_folder_id','dummy_id',
           'summary','i_thread_id','is_thread_latest'))
     OR (table_name = 'folder' AND column_name IN
          ('folder_id','parent_folder_id','sync_in_progress_folder_id')) )
ORDER BY table_name, ordinal_position;
```

Expected: `folder_id`, `item_id`, `size`, `source_folder_id`, `dummy_id` are `bigint`;
`folder` columns are `bigint`; the three added columns exist with the types above.

```sql
-- before the 14.4 upgrade this should return nothing; FK_item_folder appears after it

  AND constraint_name IN ('FK_item_folder','FK_i_item_thread');
```

### 4.8 What the installer does afterwards

With the columns already in place, the 14.4 WebClient migration detects the applied changes and
skips the rebuild; only the remaining changes run (the `item` foreign keys, `folders`,
`snoozed_item`, `thread`, and the GroupWare work). Watch the installer log to confirm:

```bash
grep -E "WebClient DB upgrade task|WebClient is ready|successfully upgraded" \
  /opt/icewarp/logs/setup/icewarp-install.log /var/log/iw/upgrade-14.4.log
```

If the `item` rebuild is still attempted, the pre-alter did not match what the migration expects —
re-check section 4.7 before proceeding rather than letting it run twice.

## 5. Servers with replicas

### 5.1 What changes when replicas exist

| Area | Implication |
|------|-------------|
| Binlog | The `item` ALTER replicates as a **single statement** (small), but every replica must **re-execute the rebuild**. The migration's orphan `DELETE` and, above all, pt-osc's row copies are row-logged: expect large binlog files, network transfer, and binlog disk usage on the primary. |
| Replica lag | A replica applies the rebuild serially; expect lag roughly equal to the rebuild time (tens of minutes on large tables). Do not plan a failover window that assumes replicas are current. |
| Reads on replicas | While the applier executes the ALTER it holds a metadata lock on `item`; queries touching that table block or hit `lock_wait_timeout` and fail. Drain or redirect read traffic from replicas for the duration. |
| Disk on replicas | Each replica needs the shadow copy too: **≥ 2× the table size free** on every replica, not just the primary. A replica that runs out of disk will stop applying. |
| Semi-sync | If a replica is slow, semi-sync commit waits can throttle the primary further. Consider raising `rpl_semi_sync_source_timeout` or disabling semi-sync for the window. |
| Durability on replicas | `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1` and doublewrite on a replica make apply slower. Relax them on replicas for the window if their crash safety is acceptable. |
| Binlog suppression | **`skip-log-bin` is not an option on a primary with replicas** — the replicas would stop receiving changes. Likewise, `--set-vars "sql_log_bin=0"` for pt-osc must not be used: the copied rows would never reach the replicas and the final `RENAME` would land on an empty shadow table there. |
| Running the DDL on replicas | Do **not** run the ALTER manually on a replica and expect the primary's statement to be a no-op — `ADD COLUMN` would fail as a duplicate. Run the change on the primary and let it replicate. |

### 5.2 What to do

1. **Keep binary logging enabled** on the primary. Use sections 2.1–2.2 for the redo/doublewrite/IO
   wins instead; they do not break replication.
2. **Tune every replica the same way** (`innodb_redo_log_capacity`, `innodb_doublewrite`,
   `innodb_io_capacity`, buffer pool). Otherwise the replica becomes the bottleneck while applying.
3. **Free disk on every replica** (≥ 2× the table) and watch it during apply:
   `df -h` on the replica's datadir.
4. **Drain read traffic** from replicas that will apply the DDL, or accept that queries on `item`
   fail with lock timeouts while it runs.
5. **Let pt-osc watch replica lag** so it pauses instead of piling on:

   ```bash
   pt-online-schema-change \
     --alter "MODIFY COLUMN folder_id BIGINT NOT NULL, \
              MODIFY COLUMN item_id BIGINT NOT NULL AUTO_INCREMENT, \
              MODIFY COLUMN size BIGINT NOT NULL, \
              MODIFY COLUMN source_folder_id BIGINT, \
              MODIFY COLUMN dummy_id BIGINT, \
              ADD COLUMN summary VARCHAR(512), \
              ADD COLUMN i_thread_id BIGINT, \
              ADD COLUMN is_thread_latest INTEGER DEFAULT 1 NOT NULL, \
              ADD INDEX IDX_item_message_id (message_id), \
              ADD INDEX IDX_item_thread_latest (folder_id, is_thread_latest, `date`), \
              ADD INDEX IDX_item_thread_id (i_thread_id)" \
     --alter-foreign-keys-method=rebuild_constraints \
     --no-check-alter \
     --chunk-time=0.5 \
     --recursion-method=dsn=D=percona,t=dsns \
     --no-check-replication-filters \
     --max-lag=30 \
     --check-interval=5 \
     --pause-file=/tmp/pt-osc.pause \
     --print --dry-run \
     h=<primary_host>,P=<port>,u=<user>,p=<password>,D=<wc_db>,t=item
   ```

   `--recursion-method=dsn=D=percona,t=dsns` discovers the replicas from the DSN table built in
   section 4.2 (this is the method that works when `PROCESSLIST`/`SHOW SLAVE HOSTS` are restricted).
   To test a single replica instead, drop `--recursion-method` and use
   `--check-replica-lag h=<replica>,P=<port>,u=<user>,p=<password>` (older Toolkit builds:
   `--check-slave-lag`). Either way pt-osc pauses when lag exceeds `--max-lag` (default 1 s — raise
   it, or the copy will stop constantly). Review with `--dry-run`, then re-run with `--execute`.

6. **Monitor replication** while the migration runs:

   ```sql
   SHOW REPLICA STATUS\G          -- Seconds_Behind_Source, Replica_SQL_Running, Last_SQL_Error
   SELECT * FROM performance_schema.replication_applier_status_by_worker;
   ```

7. **Expect one long statement per replica.** If you have several replicas, they will each spend the
   rebuild time applying it; the last one finishes roughly one rebuild *after* the primary, so size
   the window accordingly (primary + slowest replica), not just the primary.
8. **If a replica cannot keep up** (disk, IO), take it out of rotation before the window and let it
   catch up afterwards — the 14.4 DDL will replay and it will perform the rebuild itself. If it fell
   too far behind (binlogs purged), rebuild it from a fresh backup taken after the 14.4 upgrade.
9. **Backups from replicas:** if you dump from a replica, do not start the dump while that replica is
   applying the ALTER; wait until replication is caught up and the schema is consistent.

## 6. Maintenance-window checklist

1. Take a backup (dump or snapshot) of all IceWarp databases.
2. Optionally (recommended), pre-apply `folder` and then `item` with the steps in section 4 — days in
   advance, in a quiet period.
3. Apply the speed settings (section 2.2) on the primary **and every replica** and restart MySQL.
4. Drain read traffic from replicas (section 5.2).
5. Stop IceWarp on the application server (`/opt/icewarp/icewarpd.sh --stop all`).
6. Run the 14.4 installer (`sh ./install.sh --auto …` or interactively — see the note below).
7. Let the WebClient migration finish; do not restart IceWarp while it runs.
8. Wait for replicas to apply the schema changes.
9. Start IceWarp and verify accounts, WebClient, GroupWare, ActiveSync.
10. Run `ANALYZE TABLE` on `item` and the other migrated tables (section 4.6).
11. Revert the speed settings, restart MySQL (and replicas), and confirm `innodb_doublewrite=ON`,
    `innodb_flush_log_at_trx_commit=1`, and binlogging as required.
12. Re-enable backups and replication monitoring.

> **Installer note.** Automode can exit early with the "Waiting for Groupware DB" warning while the
> WebClient migration is still running. That warning is harmless, but **nothing must restart IceWarp
> until the WebClient migration finishes** (`C_WC_UpgradeStatus = 2`). Interactive mode asks before
> continuing and then waits; automode should be followed by a wait for
> `C_WC_UpgradeStatus = 2` and, if the installer exited early, `cd /opt/icewarp && ./upgrade.sh <old_version>`.

## 7. Monitoring a rebuild in progress

```sql
-- the statement currently running, its age and state
SELECT id, time, state, LEFT(info, 100) AS sql
FROM information_schema.processlist
WHERE info LIKE 'ALTER TABLE item%';

-- COPY writes a shadow table: its size tracks progress against the original
-- (run on the DB host)
--   ls -laS /var/lib/mysql/<wc_db>/item.ibd /var/lib/mysql/<wc_db>/#sql-*.ibd

-- rows written into the new table (roughly rows copied)
SHOW GLOBAL STATUS LIKE 'Innodb_rows_inserted';
```

A `state` of `copy to tmp table` means the COPY algorithm is running (expected for `item`); it
changes to index-build/rename phases near the end. Expect the shadow table to grow to roughly the
size of `item.ibd`.
